# 08-任务识别分配插件（规划，未实现）

> 状态：**仅规划，代码尚未动**。记录在这里是为了不占上下文、且下次能直接接着做。

## 1. 想做的事情

现在每次推理都要**人工指定**跑哪几张任务卡（`--tasks`）。希望反过来：
给一段文本，系统自己判断"这段该用哪些卡、按什么顺序用"，甚至把几张卡拼起来用。
目标不是多一个分类器，而是看看能不能做出**组合智能**——单卡各自普通，组合起来能答单卡答不了的问题。

## 2. 为什么 DTSeek 的架构适合做这个

关键性质：**每张卡的输入是原文，输出是原文上的坐标区间**。

- 组合不需要新模态 —— 上游输出的锚点可以直接当下游的输入或注意力约束；
- 模型零文本生成 ⇒ 组合过程不会引入幻觉（文本始终只有原文一份）；
- `feedback_proj` 已经在做"把上一步圈了什么、在哪回填给下一步"，
  跨卡组合只是让这个回填**跨卡**发生，机制是现成的。

## 3. 三个层次（逐层加难）

### 层次 A：路由卡 `dispatcher`

一张普通的 `TaskCard`，类别体系 = `[无任务, pronoun, sentiment, ownership, relation, …]`。
输出"这段文本该用哪张卡"。

**需要给协议加一个发射模式**：现有的 `emission` 只有 `single` / `pair`，
两者都必须吐起止指针。路由的输出是"任务名"而不是文本区间，所以要加
`emission="classify"`：只出 `cls_logits`，指针头照算但不计损失、不参与验收。
这是对插件协议的**自然扩展**（TaskSpec 多一个取值），解码器一行不用改。

### 层次 B：组合算子 `chain` / `pair`

让人（或配置）写组合：

- `chain(A, B)`：A 圈出的切片作为 B 的搜索范围（把 A 的锚点转成 B 的 `doc_mask`）；
- `pair(A, B)`：两张卡的结果按位置配对；
- `filter(A, B)`：B 的结果若落在 A 的锚点之外则丢弃。

运行时就是"同一个基座，按需拼装解码流程"。

### 层次 C：可学习的组合

不让人类写算子，让 dispatcher 的发射序列**本身就是程序**：
自回归地吐「算子 + 卡名 + 参数」，直到 `<eos>`。
这时 dispatcher 也是一张卡，只不过它输出的不是答案，而是**一个执行计划**。

## 4. 数据从哪来：监督信号是免费的

多任务数据集的每个样本都自带"来自哪张卡"的标签，直接就是路由器的监督信号：

- 正例：各任务卡的训练样本 + 其任务名
- 背景：不属于任何任务的普通句子（现有中性池就有）

**但这里有个陷阱**：任务数据在语体上高度可分（代词句 / 情绪句 / 成语句一看就不一样），
路由器可能只靠表面特征就拿到 99%，指标虚高却没有实际价值。
所以**验收必须带对抗集**——见下一节。

## 5. 验收指标（可判对错）

| 指标 | 说明 |
|---|---|
| `route_acc` | 路由类别正确率 |
| `route_bg_fp` | 无关句子被强行分配任务的比例 |
| `route_macro` | 每类召回的宏平均（防高频任务吃掉长尾） |
| **对抗集** | 200 条"表面像 A、实际属于 B"的构造样本；这是判"路由有没有真本事"的唯一硬指标 |
| 组合场景 | **上游召回** + **条件成功率**分开报 |

组合场景必须分开报的原因：链式组合里上游 95% × 下游 95% ≈ 90%，
一条端到端数字看不出是上游漏了还是下游错了。

## 6. 已识别的风险

1. **路由太容易** —— 见上，必须有对抗集，否则等于用 99% 包装一个无意义的结果。
2. **误差传播** —— 组合链越长越差；先限死算子集合与最大长度。
3. **组合空间爆炸** —— N 张卡、长度 L 的序列空间随 L 指数增长，训练数据不可能覆盖；
   层次 B 只做固定几个算子，层次 C 必须先做算子级别的泛化测试。
4. **基座容量不够** —— 已有实测证据：从 4 张卡加到 5 张卡时，
   `relation` 的换帧定位从 61.0% 掉到 56.3%。再加一张路由卡会继续挤。
   可能需要给 dispatcher 单独的小基座，或者共享基座但冻结。

## 7. 建议的执行顺序

1. 给 `TaskSpec` 加 `emission="classify"`（协议扩展，小改动 + 单测）
2. 做 `dispatcher` 卡 + **对抗集**，先只验收 `route_macro` 与对抗集准确率
3. 达标后再做 `chain` 算子，验收按"上游召回 + 条件成功率"分开报
4. 最后才考虑层次 C 的可学习组合

第 2 步是**决策点**：如果路由在对抗集上塌掉，说明"任务识别"这件事在
当前基座/数据下不成立，应该停在这里，而不是硬往层次 B 走。
